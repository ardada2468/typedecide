Most decisions we ask a model to make are small: route this ticket, how urgent, does this need approval. A chat model can answer, but it spends its time generating text the caller immediately parses back into an if. This page reads the answer straight out of the probability distribution instead, and runs the whole thing in your browser.

    What this does and does not show
    
  
      
    
    • The readout cannot return a malformed answer. Each criterion's softmax ranges only over its own answer letters, so an option id belonging to a different criterion is not a value it can produce. The generation lane has no such guarantee, which is what the audit column is counting.
      • 
    
    • The readout is not dramatically faster overall, and we are not going to pretend it is. Given a carefully written prompt that names every key, the generation lane answers correctly in roughly the same order of time. What the readout wins is the first decision, which lands in about a fifth of a second while generation has produced nothing usable, plus a per-option probability that generation cannot give you at all. Untick the key-naming box to see what the same lane does with a prompt that is merely reasonable.
      • 
    
    • Criteria are scored one at a time, not in one batch. ONNX Runtime's fused attention kernel refuses a batch wider than one once a past-key cache is supplied, so the parallel branch pass that a server can do is not available in any browser runtime we tested. What the prefill buys here is a shorter prompt per decision, not a single forward pass.
      • 
    
    • Timings are your hardware. They are not comparable between machines, and the first run after load is slower while shaders compile.
      • 
    
    • Accuracy is untuned. On an eight-item probe with every option order rotated, the stock weights answered 63% correctly and kept the same answer under reordering 7 times out of 8. That is a signal, not a benchmark, and it is the reason the fine-tune in train/ exists.
